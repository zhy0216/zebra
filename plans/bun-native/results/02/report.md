## 比较口径与稳定性

局部合并包括等价的输出分配/复制，没有为候选排除包装转换；候选直接返回 Uint8Array。两方都使用事先创建的同一批输入字节。完整读取两方都在计时内创建 Request、Headers、ReadableStream，并执行相同的声明长度检查、逐块实际字节限额、reader/callback/cancel/release 流程和输出消费；只改变最后合并。正文始终在限额检查后合并，传递的 `size` 是实际已限额字节数，不用 `maxLength` 截断伪装成功。小 JSON 场景测字节读取，不包含 JSON 解析。既有生产 `readBody` 也参加计时前的正确性对照。

下表列出全部场景的每次中位数（**旧 / 候选，ns/op**）及候选耗时变化 `100 × (候选中位数 / 旧中位数 − 1)`；**正数表示候选更慢**。未跨版本或跨阶段合并。大字节复制、GC 与 stream 流程会影响整体成本，局部合并和完整读取之间的差异不能被解释为因果证明。

- **可复现退化足以否决直接替换。** 空流、单 byte、小 JSON 单块/多块、16 × 1 KiB、两类偏移视图的局部合并，在四次运行各自的 9/9 配对中候选均更慢。小 JSON 单块局部中位耗时增加 202.7%–249.3%，16 × 1 KiB 增加 37.7%–42.3%。这不是只凭单次离群点作出的结论。
- **完整读取仍有退化。** 单 byte 的完整读取四次中位耗时均增加（Bun 1.4.2：4.5% / 5.4%；Bun 1.4.0：3.1% / 9.0%），分别 6/9、7/9、8/9、8/9 配对更慢。1.4.2 小 JSON 单块两次增加 7.2% / 7.1%，多块增加 5.9% / 11.5%；1.4.0 的 JSON 完整读取方向会反转，不能把某次获益作为稳定结论。
- **收益也完整保留。** 256 × 64 B 的局部合并四次均改善 27.9%–39.9%，所有配对均更快；完整读取四次改善 1.8%–8.5%。1 MiB 单块完整读取改善 10.5%–14.7%，64 × 16 KiB 改善 8.4%–15.8%。这些收益没有满足其他代表性场景不退化的条件。
- **不把小幅变化当作定论。** Bun 1.4.2 的 16 × 1 KiB 完整读取为 −3.9% / +2.2%，偏移 Uint8Array 为 −2.4% / +1.4%；Bun 1.4.0 空流为 +10.7% / −7.5%。空流第二次比值中位数看似更快，但逐对变化中位数仍是 +1.5%；因此报告同时保留逐对证据。大正文局部合并也有明显波动，与完整读取的方向不同。未设事后筛选门槛，未删除离群值，未从少数胜出的场景推导条件分支或宣称通用收益。
- 这是同机的合并/受限读取阶段测量，并非真实 HTTP 传输吞吐。虚拟化/调度、GC 与短样本噪声仍存在；9 轮两次运行不能消除全部系统噪声，但一致的代表性退化已经足以作出保守的“未采用”决定，不需要追加挑选性测量。
