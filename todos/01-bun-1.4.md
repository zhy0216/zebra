# P0 · Bun 1.4 运行时基线

条目 id：`BUN-1`

状态：`pending`

## 问题

仓库实际运行环境已经是 Bun `1.4.0`，但 CI、运行时要求和部分配置仍以 Bun `1.1.30`/`1.3` 为基线。需要把“支持哪个 Bun”变成一个一致、可机器检查的答案，并确认代码在 Bun 1.4 下没有运行时回归。

## 实现思路

1. 先全量搜索版本来源：`package.json` 的 metadata、GitHub Actions 的 setup-bun、部署 workflow、Docker 示例、基准说明和注释。区分“当前支持要求”和“历史测量记录”，不要只替换一个字符串。
2. 在根 manifest 建立唯一的运行时声明（建议 `packageManager: bun@1.4.0` 与 `engines.bun >=1.4.0`，具体字段按 Bun/发布策略验证），并审阅发布包是否需要同步暴露 `engines`。
3. 把 CI 的 full、floor、bench、coverage、docs deploy 全部切到 Bun `1.4`；移除旧的 1.1.30 floor 和“测试需要 1.3”的注释。不要保留旧版本 fallback job。
4. 审阅 `@types/bun` 的版本是否与 Bun 1.4 和后续 `tsgo` 兼容，避免继续使用无法复现的 `latest` 造成类型漂移；依赖变更只限于建立 Bun 基线所需的范围。
5. 用 Bun 1.4 重新执行安装、核心测试、构建和打包 smoke test。只有出现真实 Bun 1.4 行为差异时才改源码；不要为了旧 Bun 保留条件分支。
6. 用户文档、Docker 示例和基准 README 的正文统一由 04 改写；本文件只负责运行时 metadata、CI 配置和 Bun 1.4 的实际验证，避免两个 todo 同时编辑同一文档。

## 涉及文件（初始所有权）

- `package.json`（Bun metadata 与必要的 Bun 类型依赖）；
- `.github/workflows/ci.yml`、`.github/workflows/deploy-docs.yml`；
- 不修改 `bun.lock` 中的 Zod/tsgo 依赖；锁文件统一由后续依赖 todo 更新。若 Bun 1.4 本身改变锁格式，先记录原因再由后续 todo 合并一次生成结果；
- 不修改业务源码、Docker 示例和用户文档正文，除非验证发现 Bun 1.4 的明确回归且修复不能延后。

## 验收条件

- 所有 CI job 使用 Bun 1.4，且没有旧 Bun floor、旧版本矩阵或旧版本 fallback。
- `package.json` 的机器可读运行时要求明确最低 Bun `1.4.0`；`@types/bun` 版本可复现且与之匹配。
- 在 Bun `1.4.x` 下，以下命令至少完成一次：

  ```sh
  bun install --frozen-lockfile
  bun run build
  bun test
  bun run verify:packages
  bun run bench:check
  ```

- `git diff --check` 通过，改动没有越过本文件所有权范围。

## 风险与处理

- Bun 1.4 可能改变覆盖率、WebSocket 或 benchmark 的细节。记录失败命令和最小复现；只修复本版本回归，不降低测试阈值。
- 若锁文件必须同时包含后续依赖升级，保留可重复的 Bun 1.4 生成方式，并把 Zod/tsgo 具体变更留给后续文件，避免遗漏。
